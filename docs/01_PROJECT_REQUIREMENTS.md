## 2. コンセプト・ペルソナ

### 2.1 ユーザーペルソナ
**対象ユーザー：** 日本の学生

**具体的な特性：**
- 考えるだけで行動へつながらない人
- 計画性がなく、継続が難しい人
- 詳細にやりたいことを管理したい人

### 2.2 コアコンセプト
「思考が視覚化されて、行動へと一貫して繋げられ、完了と記録から思考プロセスの客観視ができるツール」

### 2.3 主要な問題解決パターン
**例）「貯金をしたい」というモヤモヤから実行へ**

```
モヤモヤ: 「貯金をしたい」
  ↓
  やること1: 「100万円貯金する」（期限：1年以内、重み：4）
  やること2: 「積立NISAを始める」（期限：2026年4月2日、重み：3）
  ↓
  実行 → 完了 → 「貯金というゴールにどのステップで到達したか」を記録
  ↓
  思考プロセスの客観視 → 次の意思決定に活かす
```

## 3. MVP 機能仕様

### 3.1 コア機能：「やりたいこと」管理

#### 3.1.1 基本情報
- **タイトル** （必須）
- **概要** （任意）
- **期限設定** （必須、2パターン）
  - パターンA：カレンダーで明確な日付を指定
  - パターンB：スケール選択（2週間以内 / 2ヶ月以内 / 1年以内 / いつか）
- **重み付け** （5段階、必須）
  - デフォルト：1
  - 4以上でサービス監査対象（削除時に「やらない理由」記述必須）
- **やる理由** （任意、デフォルト：「理由なんてなくても」）
  - 重み4以上の場合は必須
- **紐づくモヤモヤ** （任意）

#### 3.1.2 パス（ステップ構造）
- **必須：** 全やることに最低1つのパスを設定
- **デフォルト：** タイトルが自動的に1ステップとして設定
- **構造：** 3段階まで階層化可能
  - ステップ1（親）
    - todo1（子）
    - todo2（子）
  - ステップ2（親）

#### 3.1.3 並列タスク対応
- 1つのステップ内に最大5個程度の並列todoを配置可能
- ステップ内のtodo全てが完了 → ステップ完了判定

#### 3.1.4 進捗管理
- **ビジュアル表示**
  - 完了：グレー
  - 実行中：オレンジ
  - 未実行：白
- **自動遷移：** 前ステップ完了で次ステップが自動的に「実行中」に
- **進捗度表示：** 「3/5 ステップ完了」のような表示
- **編集機能**
  - パス追加：どのステップの間にでも追加可能
  - 並び替え：ドラッグ操作で順序変更可能

#### 3.1.5 完了フロー
1. 全ステップにチェック
2. 下部「完了ボタン」が活性化
3. 長押しで完了実行
4. **セレモニーUI：** 振動 + ハッピー絵文字が上から降ってくるアニメーション
5. 詳細画面が小さくなり、アーカイブへ遷移するアニメーション

#### 3.1.6 削除・アーカイブ時の確認
- **重み4以上の場合：** 「やらない理由」を記述必須
- **完了時：** 関連モヤモヤが解消されたかをユーザーに確認
  - 解消：モヤモヤと共にアーカイブ
  - 未解消：やることのみアーカイブ、モヤモヤは残存

### 3.2 コア機能：「モヤモヤ」管理

#### 3.2.1 基本情報
- **テキスト** （必須）
- **タグ分類** （必須）
  - 悩み
  - アイデア
  - 疑問

#### 3.2.2 自問自答UI
モヤモヤ作成後、自動的に以下の選択肢を提示：

**パターンA：「もっと深掘りしたい？」**
- ユーザーが追加テキストを記入 → 再度分岐

**パターンB：「やることが思いついた？」**
- やること新規作成フロー進行

**パターンC：「分からない/息詰まった？」**
- AIプロンプト自動生成
- 「以下の文章をコピーしてClaudeかChat-GPTに聞いてみよう」というメッセージ表示
- プロンプト例：
  ```
  「以下の悩みに対してどのようなことをやればいいでしょうか？
  【悩み】{ユーザー入力テキスト}
  【ルール】
  - 明確に判断できるやることを記述してください
  - 複数の選択肢がある場合は列挙してください
  - 内容が薄かったら、さらに深掘り質問をしてください
  推奨AI：Claude または ChatGPT」
  ```

#### 3.2.3 紐づけ
- 1つのモヤモヤ → 複数のやること（1:N）
- 複数のモヤモヤ → 1つのやること（N:1）

#### 3.2.4 アーカイブフロー
**パターンA：やることを伴わずモヤモヤが解消**
- モヤモヤ削除時に「なぜ晴れたのか」の理由を記述
- アーカイブに移動
- 思考プロセス記録：「独立した思考整理として記録」

**パターンB：やることを伴ってモヤモヤが解消**
- 最後のやること完了時に「モヤモヤは解消されたか」を確認
- 解消の場合：モヤモヤとやることを共にアーカイブ
- 思考プロセス記録：「モヤモヤ→やること→実行」という一連の思考フロー

### 3.3 画面構成（MVP段階）

#### 3.3.1 ホーム画面
- **タブバー下部に配置：** ホーム / アーカイブ / マイページ
- **コンテンツ：**
  - やりたいこと一覧
  - モヤモヤ一覧
  - （スーパーやることは概念削除、実装から除外）
- **各要素のアクション：**
  - 各項目をタップ → 詳細画面へ
  - 関連するモヤモヤ/やることが存在する場合 → アイコン表示

#### 3.3.2 詳細画面（やりたいこと）
- タイトル＋進捗度表示（「3/5 ステップ完了」）
- パス構造（ステップとtodo表示）
- 編集情報（期限、重み付け、やる理由、紐づくモヤモヤ）
- 期限超過の場合 → マーク表示

#### 3.3.3 詳細画面（モヤモヤ）
- テキスト表示
- タグ表示
- 関連やりたいこと一覧（アイコン → 詳細で確認）

#### 3.3.4 アーカイブ画面
- 完了したやりたいこと（グルーピング）
- 昇華したモヤモヤ（グルーピング）
- 各項目をタップ → 詳細（完了日、かかった期間、感想など）を確認

#### 3.3.5 マイページ
- やりたいことの数
- モヤモヤの数
- （将来：グラフ、統計情報なども追加予定）

```
┌─────────────────────────────────────────────────────┐
│                     Vercel                           │
├──────────────────────────────────────────────────────┤
│  ┌──────────────────────────────────────────────┐  │
│  │   React フロントエンド                        │  │
│  │ (ホーム、モヤモヤ管理、やりたいこと管理)      │  │

│                   ↓ (API呼び出し)                   │
│  ┌──────────────────────────────────────────────┐  │
│  │   Node.js サーバーレス関数                    │  │
│  │ (API、認証、ビジネスロジック)                │  │

└──────────────────┬──────────────────────────────────┘
                   │
                   ↓ (SQL)
┌──────────────────────────────────────────────────────┐

├──────────────────────────────────────────────────────┤
│  • users テーブル（認証）                            │
│  • mooraya テーブル（モヤモヤ）                      │
│  • tasks テーブル（やりたいこと）                    │
│  • task_steps テーブル（ステップ）                  │

│  • logs テーブル（エラーログ）                       │
└──────────────────────────────────────────────────────┘
```

### 6.2 通信フロー例

**1. ユーザー認証**
```
React → Supabase Auth → JWT トークン取得 → React 保持
```

**2. モヤモヤ作成**
```
React → Vercel API → Supabase mooraya テーブル保存
```

**3. やりたいこと作成**
```
React → Vercel API → Supabase tasks + task_steps 保存
→ mooraya_tasks テーブルで紐づけ
```

**4. 進捗更新**
```
React → Vercel API → Supabase task_steps 更新
```

**5. データ取得**
```
React → Vercel API → Supabase JOIN クエリ → React 表示
```

## 7. 実装推奨アクション

### 7.1 Cold Start 問題への対策
**問題：** Vercel サーバーレス関数は無アクセス時に休止 → 起動時に 3～5秒の遅延

**対策（MVP段階）：**
- ① **Wake-up 定期実行** — Cloudflare Workers や UptimeRobot で定期的にAPIを叩く
- ② **フロントエンドキャッシング** — React 側でデータをローカル保持、オフライン対応
- ③ **ユーザーへの告知** — UXの許容範囲内か確認

**推奨：** ①②を並行実装

### 7.2 エラーハンドリング・ログ設計

**必須対応：**
- API 各エンドポイントに try-catch 配置
- エラーを Supabase logs テーブルに記録
- ユーザーに対して適切なエラーメッセージを返却

**テンプレート例（Node.js）：**
```javascript
export default async function handler(req, res) {
  try {
    // ロジック
    return res.status(200).json({ success: true, data });
  } catch (error) {
    // ログ記録
    await supabase
      .from('logs')
      .insert({
        error_message: error.message,
        stack_trace: error.stack,
        endpoint: req.url,
        timestamp: new Date(),
      });
    
    return res.status(500).json({ 
      success: false, 
      message: 'サーバーエラーが発生しました' 
    });
  }
}
```

### 7.3 データベース設計の最適化

**重要：** モヤモヤ ↔ やりたいこと の Many-to-Many 関連性は中間テーブルが必須

```sql
-- 中間テーブル
CREATE TABLE mooraya_tasks (
  id BIGINT PRIMARY KEY,
  mooraya_id BIGINT REFERENCES mooraya(id),
  task_id BIGINT REFERENCES tasks(id),
  created_at TIMESTAMP
);
```

**設計のコツ：**
- 正規化で冗長性を排除
- インデックスを効果的に配置（外部キーなど）
- JOIN クエリの最適化を初期から意識

### 7.4 フロントエンド状態管理

**MVP段階の判断：**
- 小規模実装なら `useState` のみで十分
- 複雑化の兆候が見えたら `Zustand`（軽量な状態管理）導入

### 7.5 認証周り

**MVP段階：** Supabase Auth でメール認証のみ実装

**将来対応候補：** GitHub / Google / Discord ログイン
