## 1. テーブル一覧（概要）

このアプリケーションでは、以下の7つのテーブルでデータを管理します：

| # | テーブル名 | 役割 | 例 |
| --- | --- | --- | --- |
| 1 | `users` | ユーザー情報 | メールアドレス、ユーザーネーム |
| 2 | `mooraya` | モヤモヤ（悩み・アイデア・疑問） | 「貯金をしたい」というモヤモヤ |
| 3 | `tasks` | やりたいこと | 「100万円貯金する」というやること |
| 4 | `task_steps` | パス（ステップ） | 「目標金額を決める」というステップ |
| 5 | `task_step_todos` | ステップ内のtodo | 「親に相談する」というtodo |
| 6 | `mooraya_tasks` | モヤモヤとやりたいことの関連性 | 「貯金モヤモヤ」→「100万円貯金」と「積立NISA」に繋ぐ |
| 7 | `logs` | エラーログ | API実行時のエラーを記録 |

## 2. 詳細テーブル設計

### 2.1 `users` テーブル

**役割：** ユーザー認証情報とプロフィール

**管理する情報：**
- ユーザーID（Supabase Auth が自動生成）
- メールアドレス
- ユーザーネーム
- 作成日時
- 更新日時

**特徴：**
- Supabase Auth と自動連動（ログイン時に自動作成）
- メールアドレスはユニーク（同じメールで複数登録不可）

---

### 2.2 `mooraya` テーブル

**役割：** モヤモヤ（悩み・アイデア・疑問）を管理

**管理する情報：**
- モヤモヤID（自動採番）
- ユーザーID（誰のモヤモヤか）
- テキスト内容（「貯金をしたい」など）
- タグ（「悩み」「アイデア」「疑問」の3種類）
- 作成日時
- 更新日時
- アーカイブ日時
- アーカイブ理由（「なぜモヤモヤが晴れたのか」）

**編集・削除ルール：**
- ✅ テキスト修正・追記：**可能**（更新日時が変わる）
- ❌ タグ変更：**不可**（別のモヤモヤとして新規作成させる）
- ✅ アーカイブ：**可能**（アーカイブ理由を記述）
- ✅ アーカイブ後の削除：**可能**（2重確認必須）

---

### 2.3 `tasks` テーブル

**役割：** やりたいこと（タスク）を管理

**管理する情報：**
- やることID（自動採番）
- ユーザーID（誰のやることか）
- タイトル（「100万円貯金する」など）
- 説明（任意）
- 期限タイプ（「明確な日付」か「スケール」か）
  - `specific_date`：特定の日付
  - `within_2weeks`：2週間以内
  - `within_2months`：2ヶ月以内
  - `within_1year`：1年以内
  - `someday`：いつか
- 期限日付（明確な日付の場合のみ入力）
- 重み付け（1～5、デフォルト：1）
- やる理由（デフォルト：「理由なんてなくても」）
- 作成日時
- 更新日時
- 完了日時
- 完了時の感想（アーカイブ後に記入可能）
- アーカイブ日時

**編集・削除ルール：**
- ✅ タイトル修正：**可能**（アーカイブ前なら）
- ✅ パス追加・削除・並び替え：**可能**（アーカイブ前なら）
- ✅ 期限変更：**可能**（アーカイブ前なら）
- ✅ 重み付け変更：**可能**（アーカイブ前なら）
- ❌ 編集：**不可**（アーカイブ後は感想のみ追記可能）
- ✅ アーカイブ：**自動実行**（全ステップ完了で自動）

**期限超過対応：**
- 期限を過ぎたやること → UI上にマーク表示（ただしやること自体は削除されない）

---

### 2.4 `task_steps` テーブル

**役割：** やりたいこと内のステップ（パス）を管理

**管理する情報：**
- ステップID（自動採番）
- やることID（どのやることに属するか）
- ステップ番号（1番目、2番目...）
- ステップタイトル（「目標金額を決める」など）
- 完了フラグ（完了/未完了）
- 作成日時
- 更新日時

**編集・削除ルール：**
- ✅ ステップ追加：**可能**（アーカイブ前なら、どこにでも追加可能）
- ✅ ステップ削除：**可能**（アーカイブ前なら）
- ✅ ステップ並び替え：**可能**（ドラッグ操作で実行）
- ✅ 完了フラグ：**可能**（前ステップ完了で自動的に「実行中」に）

**自動遷移ルール：**
- 前ステップが完了 → 次ステップが自動的に「実行中」状態に

---

### 2.5 `task_step_todos` テーブル

**役割：** ステップ内の並列todo（複数の小タスク）を管理

**管理する情報：**
- TodoID（自動採番）
- ステップID（どのステップに属するか）
- Todoタイトル（「親に相談する」など）
- 完了フラグ（完了/未完了）
- 作成日時
- 更新日時

**完了判定ルール：**
- ステップ内の全todo が完了 → ステップ全体が「完了」と判定
- 例：「買い物に行く」ステップ内の「親に聞く」「妹に聞く」「メモする」が全て完了 → ステップ完了

---

### 2.6 `mooraya_tasks` テーブル

**役割：** モヤモヤ と やりたいこと の many-to-many（複数対複数）関連性を管理

**管理する情報：**
- 関連ID（自動採番）
- モヤモヤID
- やることID
- 作成日時

**特徴：**
- 1つのモヤモヤ → 複数のやることに紐づく
- 複数のモヤモヤ → 1つのやることに紐づく

**例：**
```
モヤモヤ「貯金をしたい」
  ├─ やること「100万円貯金する」
  └─ やること「積立NISAを始める」
```

---

### 2.7 `logs` テーブル

**役割：** エラーログを記録（デバッグ・保守用）

**管理する情報：**
- ログID（自動採番）
- ユーザーID（誰がエラーを踏んだか）
- エラーメッセージ
- スタックトレース（エラーの詳細情報）
- エンドポイント（どのAPI機能で発生したか）
- HTTPステータスコード
- 発生日時

## 3. テーブル間の関連性図

```
┌──────────────────────────────────────────────────────┐
│                    users（ユーザー）                  │
│  id（PK） | email | username | created_at | ...      │
└─────────┬────────────────────────────────────────────┘
          │
          ├─────────────────────┬──────────────────────┐
          │                     │                      │
          ↓                     ↓                      ↓
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│   mooraya        │  │    tasks         │  │     logs         │
│  （モヤモヤ）    │  │ （やりたいこと） │  │  （エラーログ）  │
│ id（PK）         │  │ id（PK）         │  │ id（PK）         │
│ user_id（FK）    │  │ user_id（FK）    │  │ user_id（FK）    │
│ content          │  │ title            │  │ error_message    │
│ tag              │  │ deadline_type    │  │ stack_trace      │
│ ...              │  │ weight           │  │ endpoint         │
└────────┬─────────┘  │ ...              │  │ ...              │
         │            └────────┬─────────┘  └──────────────────┘
         │                     │
         └──────┬──────────────┘
                │
    ┌───────────┴────────────┐
    │                        │
    ↓                        ↓
┌────────────────────┐  ┌─────────────────┐
│  mooraya_tasks     │  │  task_steps     │
│（関連性管理）      │  │ （パス・ステップ）
│ id（PK）           │  │ id（PK）        │
│ mooraya_id（FK）   │  │ task_id（FK）   │
│ task_id（FK）      │  │ step_number     │
│ ...                │  │ title           │
└────────────────────┘  │ completed       │
                        │ ...             │
                        └────────┬────────┘
                                 │
                                 ↓
                    ┌────────────────────────┐
                    │  task_step_todos       │
                    │ （ステップ内のtodo）   │
                    │ id（PK）               │
                    │ step_id（FK）          │
                    │ title                  │
                    │ completed              │
                    │ ...                    │
                    └────────────────────────┘
```

**凡例：**
- `PK`：プライマリキー（ユニークID）
- `FK`：フォーリンキー（他のテーブルへの参照）

## 4. 重要な業務ロジック

### 4.1 モヤモヤ解消判定（複雑なビジネスロジック）

**状況：** 1つのモヤモヤから複数のやることが出ている

**例：**
```
モヤモヤ「貯金をしたい」
  ├─ やること「100万円貯金する」← ステップ1,2,3... 全て完了
  └─ やること「積立NISAを始める」← ステップ1,2... (未完了)
```

**フロー：**

1. **やること「100万円貯金する」が完了**
   - UI上に「まだやることがあります！」と表示
   - モヤモヤはアーカイブされない
   - ユーザーにアクション要求なし

2. **やること「積立NISAを始める」も完了**
   - 全やることが完了した時点で、ユーザーに確認
   - 「モヤモヤ『貯金をしたい』は解消されましたか？」と質問

3. **ユーザーが「解消された」と答えた場合**
   - モヤモヤ + 全やることを共にアーカイブ
   - 思考プロセス記録：「モヤモヤ→複数やること→実行→解消」

4. **ユーザーが「まだ解消されていない」と答えた場合**
   - やることのみアーカイブ
   - モヤモヤは残存
   - ユーザーは新しいやることを追加可能

---

### 4.2 期限超過対応

**条件：** 今日の日付が期限を過ぎている

**対応：**
- ✅ やること一覧画面：マーク表示（例：⚠️ マーク）
- ✅ やること詳細画面：「期限：2026年2月10日（超過中）」と表示
- ℹ️ ただし、やること自体は削除されない（継続実行可能）

---

### 4.3 重み付けと監査ルール

**重み付け 4以上の場合：** サービス側で「監査」が働く

**削除時の監査：**
- 重み4以上のやることを削除しようとする
- 削除前に「このやることをやらない理由を教えてください」と強制
- ユーザーが理由を記述 → 初めて削除可能

**このロジックにより：** ユーザーの「合理化による離脱」を防ぐ

---

### 4.4 アーカイブ後の操作

**アーカイブに移動したやること：**
- ❌ タイトル・説明・パスなどは編集不可
- ✅ 感想のみ追記可能
- ✅ アーカイブ後に削除可能（2重確認必須）

**アーカイブに移動したモヤモヤ：**
- ❌ テキスト修正不可
- ✅ アーカイブ後に削除可能（2重確認必須）

## 5. データ型と制約

### 5.1 各カラムのデータ型（参考情報）

| テーブル | カラム名 | データ型 | 説明 |
| --- | --- | --- | --- |
| users | id | UUID | ユーザーID（Supabase Auth が自動生成） |
| users | email | TEXT | メールアドレス（ユニーク） |
| users | username | TEXT | ユーザーネーム |
| mooraya | id | BIGINT | モヤモヤID（自動採番） |
| mooraya | tag | VARCHAR(50) | 「worry」「idea」「question」のいずれか |
| tasks | deadline_type | VARCHAR(20) | 期限タイプ |
| tasks | weight | INT | 重み付け（1～5） |
| task_steps | completed | BOOLEAN | 完了フラグ |

## 6. MVP実装での注意点

### 6.1 リアルタイム同期の考慮

Supabase は **リアルタイムリッスン機能**を持っています。例えば、ステップを完了したら、フロントエンド側で自動的に「次のステップ」が「実行中」に変わる、という動きが実装可能です。

**MVP段階：** ページ再読込で対応（実装簡易化）  
**将来：** リアルタイム機能を追加（UX向上）

### 6.2 インデックスと検索パフォーマンス

今後ユーザーが増えた場合、以下のインデックスを配置予定：
- `mooraya` テーブルの `user_id`（高速検索）
- `tasks` テーブルの `user_id`（高速検索）
- `mooraya_tasks` の `mooraya_id` と `task_id`（関連データの高速結合）

**MVP段階：** Supabase デフォルトのインデックスで対応
